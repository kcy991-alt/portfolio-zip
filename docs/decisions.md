# 결정 로그

## 2026-10-07 — 기술 스택: Next.js + Supabase + Vercel

- **정한 것**: 웹은 Next.js(App Router)+TypeScript, 인증·DB·파일 저장은 Supabase(Auth/Postgres/Storage), 배포는 Vercel로 간다. spec.md 15장의 제안 스택을 사용자가 그대로 받아들였다.
- **이유**: 사용자가 Vercel과 Supabase 위주로 가길 원했다. 한 곳에서 화면·서버 API·로그인·권한(RLS)·이미지 저장이 해결되어 바이브코딩 MVP에 맞다.
- **다른 선택지**: Firebase(문서형 DB라 관계형 데이터와 RLS 같은 권한 설계가 어렵다), 직접 서버 구축(운영 부담이 크다).

## 2026-10-07 — 이메일 발송 방식: Supabase 커스텀 SMTP, Next.js 서버는 P1부터

- **정한 것**:
  - P0의 인증 메일(가입 확인·비밀번호 재설정)은 Supabase Auth가 보낸다. SMTP 제공자는 Supabase 대시보드(Authentication > Emails > SMTP Settings)에 연결하며, Next.js 코드에는 SMTP 로직을 넣지 않는다.
  - 앱이 직접 메일을 보내야 하는 기능(P1 기록 리마인더 등)은 Next.js 서버(Node.js 런타임 route handler 또는 server action)에서 보낸다. 발송 코드는 `src/lib/email/` 한 곳에 모으고, 제공자는 바꿀 수 있게 인터페이스로 분리한다.
  - 앱에서 직접 보낼 때는 제공자의 HTTP API를 우선한다. SMTP가 꼭 필요하면 nodemailer를 쓰되 `runtime = 'nodejs'`, 포트 465/587, `await` 방식으로 호출한다.
  - SMTP 제공자(예: Resend)는 아직 확정하지 않았다.
- **이유**:
  - 브라우저(FE)는 SMTP 소켓을 직접 열 수 없고, 열 수 있어도 자격증명이 노출된다. 그래서 발송은 반드시 서버 쪽에서 한다.
  - Vercel 함수(Node.js 런타임)는 465/587 포트 SMTP가 가능하다. 25번 포트는 막혀 있고, Edge 런타임은 TCP 소켓이 없어 SMTP를 못 쓴다.
  - Supabase 기본 메일은 프로젝트 전체에서 시간당 2통 수준이라 베타에 쓸 수 없다. 커스텀 SMTP를 연결하면 시간당 30통에서 시작하고 대시보드에서 올릴 수 있다.
  - P0에는 앱이 직접 보내는 메일이 없어서 코드 없이 설정만으로 끝난다.
- **다른 선택지**:
  - Supabase Send Email Hook으로 Next.js route handler가 인증 메일까지 직접 발송: 메일 문구·발송 경로를 완전히 통제할 수 있지만, 훅 서명 검증과 장애 처리를 직접 만들어야 해서 P0에는 과하다.
  - Next.js에서 nodemailer로 SMTP 직접 발송: 가능하지만 서버리스에서 연결이 중간에 끊길 수 있어 HTTP API보다 불안정하다.
  - Supabase 기본 메일 유지: 발송 한도 때문에 제외.
- **환경변수 영향**: P0는 추가 없음. SMTP 자격증명은 Supabase 대시보드에만 입력한다. P1에서 앱이 직접 발송할 때 제공자 키 하나를 서버 전용 환경변수로 추가한다(`NEXT_PUBLIC_` 접두사 금지).

## 2026-10-07 — 이메일 단계별 계획: 개발 중엔 이메일 확인 끄기, 도메인·Resend는 베타 직전

- **정한 것**:
  - 개발·시연 단계에서는 Supabase의 "Confirm email"을 끄고, 가입하면 바로 로그인되게 한다. 도메인은 아직 사지 않는다.
  - 외부 사용자 베타 전에 도메인을 구매해 Vercel과 Resend에 연결한다. 발송용으로는 서브도메인(예: `mail.도메인`)을 쓴다. 그때 Resend를 Supabase 커스텀 SMTP로 연결하고(`smtp.resend.com`, 465, 사용자명 `resend`, 비밀번호는 Resend API 키), "Confirm email"을 다시 켠다.
  - 인증 메일 링크는 Next.js `/auth/confirm` 경로로 받아 토큰 해시를 서버에서 검증한다(메일 보안 프로그램이 링크를 미리 열어 토큰이 소모되는 문제를 줄이기 위해). 이 경로는 베타 전 이메일 확인을 켜는 시점까지 만든다.
  - 인증 메일에 쓸 주소(`APP_ORIGIN`, Supabase Site URL·Redirect URLs)는 고정된 프로덕션 주소를 쓴다. Vercel의 커밋별 주소는 배포마다 바뀌므로 쓰지 않는다. 미리보기 배포는 Redirect URLs에 와일드카드 패턴으로 허용한다.
  - Send Email Hook으로 메일을 직접 만드는 방식은 P1로 미룬다.
- **이유**:
  - 아직 제품 도메인이 없다. `vercel.app` 도메인은 Vercel 소유라 Resend에서 도메인 인증에 쓸 수 없을 가능성이 높다(Resend는 직접 소유한 도메인을 요구한다).
  - 개인과제 시연이 먼저라서, 도메인 구입 전까지 가입·로그인 흐름 개발을 막지 않으려는 목적이다.
  - Supabase 기본 메일은 프로젝트 전체에서 시간당 2통이라 개발용으로도 불안정하다.
- **다른 선택지**: 처음부터 도메인을 사서 Resend 연결(비용과 준비가 먼저 필요), Supabase 기본 메일로 확인 메일 유지(발송 한도 때문에 사실상 불가).
- **알아둘 점**:
  - 이메일 확인과 비밀번호 재설정 메일은 spec.md F01의 P0 인수 조건이다. 개발 단계에서는 이 조건을 일시적으로 충족하지 않는다. 비밀번호 재설정은 도메인 연결 전까지 동작하지 않거나 제한된다.
  - 이메일 확인이 꺼진 상태에서는 존재하지 않는 이메일로도 가입이 된다. 외부 사용자에게 공개하기 전에 반드시 켠다.
  - spec.md는 수정하지 않았다. 필요하면 12장·16장(D2)과 F01에 이 단계 구분을 반영할지 사용자에게 먼저 묻는다.

## 2026-10-07 — 프로젝트 초기화와 D0 질문 구조 정의

- **정한 것**:
  - Next.js(App Router)+TypeScript+Tailwind 프로젝트를 `src/` 구조로 만들고 Zod, Vitest를 설치했다. 패키지 관리자는 npm이다. `.env.example`에는 spec 12.2의 키 이름만 비워 두고, `.env*`는 git에서 제외하되 `.env.example`만 올린다.
  - 질문 구조는 `src/lib/validation/project-answers.ts`(Zod 스키마)와 `src/templates/pm-v1/index.ts`(10개 단계, 출력 구역 매핑, 수치 없을 때 가이드 문구)에 정의했다. 모든 필드는 빈 값을 허용해 초안 저장이 가능하다.
  - 스키마에서 spec이 정하지 않은 부분은 이렇게 채웠다. `teamSize`는 짧은 문자열(40자), 지표의 baseline/target/actual은 문자열(200자)이다. 숫자로 강제하면 "약 3명", "2주 단위" 같은 실제 표현을 막기 때문이다.
  - 핵심 필드는 `overview.oneLine`, `role.responsibility`, `problem.phenomenon`, `contribution`, `result.status`로 잡았다(프로젝트명은 `project.title`). spec 1.3의 "프로젝트명, 역할, 문제, 직접 행동, 결과 상태"를 이 필드들에 대응시킨 해석이며, 품질 점수가 아니라 누락 확인용이다.
- **이유**: spec 20-2의 "먼저 질문 schema·결과 상태·템플릿 구역·원본/사본 데이터 계약을 만든다"를 따랐다. 스키마, 단계, 출력 구역이 서로 어긋나지 않는지는 `tests/template.test.ts`가 확인한다.
- **다른 선택지**: 지표 값을 숫자 필드로 강제(실제 표현 입력이 어려워짐), pnpm 사용(사용자 환경에 맞춘 기본 npm 유지).
- **알아둘 점**: 이 Next.js 버전은 문서(`node_modules/next/dist/docs/`)를 먼저 읽고 코드를 쓰라는 안내(AGENTS.md)가 들어 있다. D1 이후 Next.js 코드를 쓸 때 해당 문서를 확인한다.
## 2026-10-07 — D1 샘플 화면 구현 방식

- **정한 것**:
  - 경로는 `/`, `/workspace`, `/workspace/projects/[id]` 세 개로 하고, 데이터는 `src/lib/sample/data.ts`의 가상 샘플만 쓴다. 입력은 브라우저 메모리에만 있고 새로고침하면 사라진다.
  - 입력 폼은 하드코딩하지 않고 `src/templates/pm-v1/fields.ts`의 정의로 만든다. 질문 키·출력 구역·입력 필드가 한 정의에서 나오게 해서(spec 15.2의 `TemplateDefinition` 방침) 테스트(`tests/fields.test.ts`)가 스키마와 어긋남을 잡아낸다.
  - 이 Next.js 버전은 Cache Components가 켜져 있어서, `params`와 `usePathname()`을 쓰는 부분은 `<Suspense>`로 감싼다. D3에서 실제 DB를 읽을 때도 같은 구조를 쓴다.
  - 새 폴더·새 프로젝트·포트폴리오 제작·휴지통 버튼은 비활성화하고 "준비 중"이라고 표시했다. 가짜로 동작하는 것처럼 보이지 않게 하려는 spec 20-7에 따른 것이다.
  - 구역 이름 중 "프로젝트 정보"(프로젝트명·기간·유형·상태)는 spec 9.1에 있는 구역이지만 질문 섹션이 아니라서, `overview` 섹션이 이 구역에도 연결되도록 했다.
- **이유**: spec 16장 D1은 가상 샘플로 탐색기·질문·미리보기 UI를 만들고 현재 구역 강조를 확인하는 단계다. 저장은 D3에서 같은 계약으로 연결한다.
- **다른 선택지**: 화면마다 폼을 직접 작성(섹션 12개가 중복되고 스키마와 어긋날 위험), `generateStaticParams`로 샘플 id를 미리 만들기(D3에서 DB id로 바꿀 때 구조를 다시 짜야 함).
- **알아둘 점**: 미리보기는 편집용 윤곽이고 16:9 출력 렌더러는 D5 범위다. 이미지 첨부는 D2 이후라서 "대표 이미지" 구역은 자리만 표시한다. 개발 서버 확인은 데스크톱(1,280px)과 모바일(375px, 가로 넘침 없음)에서 했다.
## 2026-10-08 — Stitch 시안 채택 범위

- **정한 것**: Google Stitch로 만든 시안(화면 15개)에서 spec.md P0 범위에 맞는 화면 구성·레이아웃·토큰만 채택한다. 소셜 로그인, SSO, 2단계 인증, 요금제, 프로젝트 한도, 공유 링크, ZIP 내보내기, AI 요약, 슬라이드 테마 같은 범위 밖 기능과, 근거 없는 문구(보안 인증·암호화 등급·"전달력 2배"·채용 평균 분량 등)는 모두 제외한다. 자세한 채택·제외 목록은 `docs/design.md`에 있다.
  - 서체는 한글 서체(Noto Sans KR 우선)로 통일한다. 시안의 `Plus Jakarta Sans`는 한글을 지원하지 않아 쓰지 않는다.
  - 용어는 "슬라이드" 대신 "페이지"를 쓴다.
  - 확정한 디자인을 D1 샘플 화면에 적용하고, 시작 화면(`/`), 로그인·가입(`/auth`), 첫 방문 안내(`/welcome`), 빈 보관함(`/workspace/empty`) 샘플 화면을 추가한다.
- **이유**: 시안이 spec 14·8장의 토큰과 화면 구성을 잘 따랐지만, 구현되지 않을 기능이나 사실이 아닌 문구를 그대로 두면 사용자에게 약속하지 못할 것을 보여 주게 된다(spec 문서 사용 규칙, 20-7).
- **다른 선택지**: 일부 기능을 "준비 중"으로 비활성화해서 보여 주기(화면이 복잡해짐), spec을 바꿔서 일부 기능을 P0에 포함하기(범위 확대). 사용자가 "전부 제외"를 선택했다.
- **알아둘 점**: 로그인·새 프로젝트 창·포트폴리오 제작 등은 D1에서는 화면만 있고 저장되지 않는다. Stitch에 없는 화면(인증 메일 대기, 비밀번호 재설정, 근거 카드, 페이지 A~D 본문, 추가·확인 창)은 시안을 더 만든 뒤 반영한다.
## 2026-10-08 — 로그인은 Google만 사용 (이메일·비밀번호 가입 폐기)

- **정한 것**:
  - 로그인 방식은 Supabase Auth의 Google 로그인 하나로 한다. 이메일·비밀번호 가입, 이메일 확인, 비밀번호 재설정은 만들지 않는다. 카카오 로그인은 지금은 넣지 않는다(나중에 검토).
  - 그에 따라 앞서 기록한 "이메일 발송 방식: Supabase 커스텀 SMTP"와 "이메일 단계별 계획: Confirm email 끄기, 도메인·Resend는 베타 직전" 항목은 폐기한다. 인증에 SMTP, Resend, 도메인 구입이 필요 없고, Supabase의 이메일 로그인 제공자는 꺼 둔다. 앱이 직접 메일을 보내는 P1 기능(기록 리마인더 등)은 필요해질 때 다시 정한다.
  - `/auth` 화면은 "Google로 시작하기" 버튼 하나와 안내 문구로 바꿨고, 개인정보 처리 안내 샘플 초안(`/privacy`)을 추가했다. 지금 버튼은 계정을 만들지 않고 다음 화면으로 넘어가는 샘플 동작이며, 실제 Google 로그인은 D2에서 연결한다.
  - 계정 삭제(spec F14)의 본인 확인은 비밀번호 재입력 대신 Google로 다시 로그인하는 방식으로 한다.
  - 사용자가 Google 계정을 쓰고 싶지 않은 경우의 대안은 만들지 않는다.
- **이유**: 이메일 방식은 SMTP, 도메인, 확인·재설정 화면, 가짜 가입 방지까지 부담이 크다. Google 로그인은 이메일을 받을 수 있어서 카카오와 달리 계정 구분 문제가 없고, `vercel.app` 주소로도 인증이 되어 도메인 구입을 미룰 수 있다.
- **다른 선택지**: Google+카카오(카카오는 일반 앱이 이메일 동의 항목을 쓰기 어렵고 같은 사람의 계정이 둘로 나뉠 수 있어 보류), 이메일 로그인 유지(위 부담), 매직링크(이메일 발송이 필요).
- **알아둘 점**:
  - spec.md의 F01(이메일 로그인), F14(비밀번호 재확인), 12장 SMTP 줄, 16장 D2 문구가 이 결정과 어긋난다. spec.md는 사용자 문서라서 고치지 않았고, 고칠지 사용자에게 먼저 묻는다.
  - D2 전에 사용자가 해야 할 일: Supabase 프로젝트 생성, Google Cloud에서 OAuth 클라이언트와 동의 화면 설정(공개 전에는 테스트 사용자만 로그인 가능), Google 클라이언트 ID·비밀키를 Supabase 대시보드에 입력. 이 키들은 코드에 넣지 않는다.
  - 개인정보 처리 안내는 서비스 공개 전에 정식 문구와 문의처를 확정해야 한다.
## 2026-10-08 — spec.md를 v0.2로 수정 (Google 로그인 반영)

## 2026-10-08 — D2 첫 단계: Google 로그인 연결 방식

- **정한 것**:
  - `@supabase/supabase-js`와 `@supabase/ssr`을 쓴다. 브라우저용(`src/lib/supabase/client.ts`)과 서버용(`server.ts`) 클라이언트를 나눴고, 둘 다 사용자 세션으로 동작해서 RLS가 적용된다. secret 키는 아직 쓰지 않는다(탈퇴·정리 작업에서만 쓴다는 spec 12.2 방침 유지).
  - 로그인 흐름: `/auth`의 "Google로 시작하기" → Supabase → Google → `/auth/callback`에서 코드를 세션으로 교환 → 첫 로그인(계정 생성과 로그인 시각이 1분 이내)이면 `/welcome`, 아니면 `/workspace`. 취소·실패하면 `/auth?error=...`로 돌아와 안내 문구를 보여 준다.
  - 이 Next.js 버전은 `middleware`가 `proxy`로 이름이 바뀌어서 `src/proxy.ts`에서 세션 갱신과 접근 차단을 한다. 로그인하지 않은 사용자가 `/workspace`·`/welcome` 아래에 접근하면 `/auth`로, 로그인한 사용자가 `/auth`에 오면 `/workspace`로 보낸다. 세션은 쿠키 값을 그대로 믿지 않고 `getClaims()`로 서버에서 토큰 서명을 검증한다.
  - 로그아웃은 `POST /auth/signout`이고 사이드바 아래에 로그인 이메일과 로그아웃 버튼을 둔다.
- **이유**: spec F01(로그인하지 않은 사용자는 개인 화면 접근 불가)과 13장(UI 가드·API 인증·RLS 다층 방어)을 따르기 위해서다. 보호는 화면 숨김만으로 하지 않고 요청 단계(proxy)에서 한다. 이후 API와 데이터 조회에서도 서버 세션을 다시 검증한다.
- **다른 선택지**: 클라이언트에서만 로그인 상태를 확인(우회가 쉬움), 쿠키 값만 보고 로그인 판단(위조 가능), 서버 컴포넌트마다 개별 확인(빠뜨릴 위험).
- **알아둘 점**:
  - 지금은 Google 동의 화면이 "테스트 중"이라 등록한 테스트 사용자만 로그인된다. 공개 전에 게시 상태를 바꿔야 한다.
  - 로그인 후 보이는 프로젝트·폴더는 아직 샘플 데이터이고, 기록 저장은 D3에서 연결한다.
  - 개발 서버로 확인한 것: 비로그인 상태에서 `/workspace`, `/welcome`, `/workspace/empty`, 샘플 프로젝트 화면이 모두 `/auth`로 이동하고, `/`와 `/privacy`는 열린다. "Google로 시작하기"는 Google 로그인 화면으로 이동하며 콜백 주소가 Supabase 주소로 맞게 전달된다. 실제 계정으로 로그인해 돌아오는 부분은 사용자가 직접 확인해야 한다.
## 2026-10-08 — D2 데이터베이스·접근 제한·이미지 저장 설계

- **정한 것**:
  - 이번 마이그레이션(`supabase/migrations/20261008000000_core_schema.sql`)은 워크스페이스, 폴더, 프로젝트, 이미지, 프로젝트-이미지 연결, 삭제 작업 큐, 제품 이벤트 표를 만든다. 포트폴리오 제작본 관련 표는 D4에서 별도 마이그레이션으로 만든다(쓰이는 시점에 맞춰 만들기 위해).
  - 접근 제한: 모든 표에 RLS를 켜고 로그인한 사용자는 `owner_id`가 자기 자신인 행만 읽고 쓴다. 로그인하지 않은 사용자(anon)의 권한은 모두 회수했다. 수정할 때는 기존 행과 수정 후 소유권을 모두 검사한다. 삭제 작업 큐는 사용자가 읽기만 하고 쓰기는 서버 전용 키로만 한다.
  - 소유자가 섞이지 않게 하려고 `(대상 id, owner_id)` 쌍으로 연결하는 복합 외래키를 썼다. 그래서 남의 폴더에 내 프로젝트를 넣거나 남의 워크스페이스에 폴더를 만드는 것이 데이터베이스 수준에서도 막힌다. 폴더가 지워지면 그 안의 프로젝트는 지워지지 않고 미분류(`folder_id` 없음)로 돌아간다(spec F02).
  - 저장 충돌(spec 10.3): 프로젝트가 수정될 때마다 데이터베이스 트리거가 `revision`을 1 올린다. 앱은 `update ... where id = ? and revision = ?`로 저장하고 0행이면 409로 처리한다. 앱 코드가 revision을 올리는 것을 잊어도 충돌 검사가 깨지지 않게 하려는 목적이다.
  - 새 사용자가 만들어지면 트리거가 워크스페이스를 자동으로 만든다. 이미 로그인해 본 사용자에게는 마이그레이션이 만들어 준다.
  - 이미지: 비공개 저장소(`portfolio-assets`), 경로는 `{사용자 id}/{이미지 id}.{확장자}`, 저장소에도 같은 소유자 제한을 건다. 업로드는 서버(`POST /api/assets/upload`)에서 받아 실제 이미지인지 해독해서 확인하고(파일 이름·브라우저가 알려 준 형식은 믿지 않는다), 4,096px 안으로 줄이고 다시 인코딩해서 EXIF 등 메타데이터를 지운 뒤 저장한다. 계정당 500MB 한도를 확인한다. 이미지 주소는 `GET /api/assets/:id/read-url`에서 소유권을 확인한 뒤 10분짜리 서명 주소로 준다. 남의 이미지와 없는 이미지는 같은 404로 답한다.
  - 응답 형식은 spec 11장대로 성공은 `{ data }`, 실패는 `{ error: { code, message } }`이다.
- **이유**: spec 10장(저장 모델), 12.2(RLS), 7.5(이미지), 13장(사용자 간 격리)을 따르기 위해서다. 로그인 확인만으로는 부족하고 데이터베이스와 저장소가 스스로 남의 데이터를 막아야 한다.
- **다른 선택지**: 모든 표(제작본 포함)를 한 번에 만들기(D4까지 쓰이지 않는 표가 먼저 생김), 소유권 검사를 앱 코드로만 하기(코드 실수 한 번에 남의 데이터가 노출됨), 브라우저에서 저장소에 직접 업로드(재인코딩과 메타데이터 제거를 서버에서 보장할 수 없음).
- **알아둘 점 — spec과 어긋나는 부분(사용자 결정 필요)**:
  - Vercel 함수는 요청 본문이 4.5MB를 넘으면 앱 코드에 닿기 전에 거절한다. spec 7.5의 "첨부당 10MB"를 그대로 받으려면 방식을 바꿔야 한다. 지금은 업로드 API가 4MB까지만 받는다. 선택지는 (가) 브라우저에서 올리기 전에 4MB 안으로 줄이기(10MB 원본도 선택 가능), (나) 저장소에 임시로 직접 올린 뒤 서버가 내려받아 처리하기(복잡하지만 10MB 유지), (다) spec의 한도를 4MB로 낮추기이다.
  - spec 13장의 업로드 요청 제한(계정당 분당 10회)과 11장의 중복 업로드 방지(client operation ID)는 아직 만들지 않았다. D3·D6에서 만든다.
  - 업로드 중 데이터베이스 등록이 실패하면 방금 올린 파일을 바로 지운다. 이 정리까지 실패한 경우를 위한 삭제 작업 큐 처리는 D3·D6에서 만든다.
  - 실제 Supabase에는 SQL을 사용자가 대시보드에서 직접 실행해야 한다. 실행 뒤 `supabase/tests/rls-isolation.sql`로 사용자 A/B 격리를 확인한다(통과해야 D2 완료).
  - 개발 서버에서 확인한 것: 비로그인 상태에서 업로드·이미지 주소 API가 모두 401을 JSON으로 돌려주고, 이미지 처리 함수는 단위 테스트 6개(크기 줄이기, 메타데이터 제거, SVG·GIF·텍스트 거절, 용량 제한)를 통과했다. 로그인 상태의 업로드와 데이터베이스 격리는 SQL 실행 뒤 확인한다.
## 2026-10-08 — 로그인 없이 둘러보기, 저장할 때만 로그인

- **정한 것**:
  - 로그인하지 않아도 시작 화면, 첫 방문 안내, 경험 보관함, 경험 편집 화면을 모두 볼 수 있다. 이때는 가상의 샘플 데이터만 보이고, 입력은 화면에서만 유지되며 서버에 저장되지 않는다. 폴더·프로젝트 만들기, 저장 같은 저장 동작을 누를 때만 "저장하려면 로그인이 필요해요" 안내를 띄우고 Google 로그인으로 보낸다. 안내에는 지금 입력한 내용이 로그인 과정에서 사라진다고 밝힌다.
  - 앞서 만든 "로그인하지 않으면 `/workspace`·`/welcome`을 `/auth`로 보냄" 규칙은 없앴다. `src/proxy.ts`는 세션을 갱신하고, 이미 로그인한 사용자가 `/auth`에 오면 보관함으로 보내는 일만 한다.
  - 보안 경계는 그대로다. 저장된 데이터는 서버 API(로그인 확인)와 DB(RLS)가 막으므로, 둘러보기 화면에서 API를 직접 불러도 401을 받는다. 화면의 로그인 상태 표시(`AuthProvider`)는 편의용이며 보안 판단에 쓰지 않는다.
  - 시작 화면의 "바로 시작하기"는 `/welcome`(3단계 안내)으로, 안내가 끝나면 `/workspace`(샘플 보관함)로 간다. `/auth`에는 "로그인 없이 둘러보기" 링크를 둔다.
  - 로그인한 사용자에게는 저장 버튼들이 저장 기능이 연결되기 전(D3)까지 "(준비 중)"으로 비활성화되어 있다.
  - spec.md를 v0.3으로 올렸다: F01 문구 수정, F15(로그인 없이 둘러보기) 추가, 8.1 화면 설명과 13장 인증·권한 행 수정.
- **이유**: 사용자가 로그인을 처음부터 강요받지 않고 서비스가 어떻게 구성되어 있는지 먼저 보고, 저장하고 싶을 때만 로그인하기를 원했다. 로그인 장벽이 첫 사용 경험의 진입을 막는 것을 줄이려는 목적이다.
- **다른 선택지**: 모든 화면을 로그인 필수로 유지(진입 장벽), 둘러보는 동안 입력한 내용을 브라우저에 보관했다가 로그인 후 옮겨 주기(spec 10.3의 P0 제외 범위인 로컬 영구 보관에 해당하고 공용 컴퓨터에 내용이 남을 수 있어 이번에는 하지 않음).
- **알아둘 점**: 둘러보기 중에 쓴 내용은 로그인하면 사라진다. 이를 줄이려면 로그인 직전에 내용을 임시로 옮겨 주는 기능을 나중에 검토할 수 있다. 개발 서버에서 확인한 것: 비로그인으로 보관함과 편집 화면이 열리고, "새 프로젝트"·"저장"을 누르면 로그인 안내가 뜨며 Esc로 닫힌다. 입력은 유지되고, 업로드 API는 401을 돌려준다.
## 2026-10-08 — 이미지 업로드: 브라우저에서 줄여서 올리기 (사용자가 (가) 방안 선택)

- **정한 것**: 사용자는 10MB까지 원본을 고를 수 있고, 브라우저가 올리기 전에 4,096px 이하·약 3.5MB 이하로 줄여서 서버로 보낸다(`src/lib/storage/client-compress.ts`). 용량이 이미 작으면 그대로 보내고, 크면 WebP(투명도 유지)로 품질을 낮춰 가며 목표 크기에 맞춘다. WebP를 못 만드는 브라우저는 JPEG(흰 배경)로 대신한다. 서버는 4MB를 넘는 요청을 413으로 거절하고, 받은 파일은 다시 실제 이미지인지 검증하고 재인코딩해서 메타데이터를 지운다. spec 7.5를 v0.4로 보완했다.
- **이유**: Vercel 함수는 요청 본문이 4.5MB를 넘으면 앱 코드에 닿기 전에 거절한다. 브라우저에서 줄이면 구조를 복잡하게 하지 않고도 사용자가 10MB 원본을 그대로 고를 수 있다.
- **다른 선택지**: 저장소에 직접 올린 뒤 서버가 내려받아 처리(10MB를 그대로 지원하지만 구조와 정리 작업이 복잡함), spec 한도를 4MB로 낮추기(사용자가 직접 줄여야 함).
- **알아둘 점**: 줄이는 작업이 브라우저에서 일어나므로 매우 큰 이미지는 기기에 따라 느릴 수 있다. 서버는 브라우저가 보낸 것을 믿지 않고 다시 검증하므로 보안 경계는 그대로다. 줄이는 함수의 크기 계산과 입력 검사는 단위 테스트(`tests/client-compress.test.ts`)로 확인했고, 실제 줄이기 동작은 업로드 화면을 만드는 D3에서 브라우저로 확인한다.
## 2026-10-08 — D2 완료: 데이터베이스 격리 검사 통과

- **정한 것**: Supabase에 `core_schema.sql`을 실행했고, `rls-isolation.sql`(사용자 A/B 격리 검사)이 `ALL PASSED (rolled back)`로 통과했다. 이로써 spec 16장 D2의 완료 조건 중 "사용자 A/B 격리 확인", "키 노출 없음"(publishable 키만 사용), "Google 로그인 동작"을 만족한다.
- **확인된 것**: 새 사용자의 워크스페이스 자동 생성, 프로젝트 수정 시 revision 증가, 다른 사용자의 폴더·프로젝트 읽기·수정·삭제 차단, 소유자·워크스페이스·폴더를 바꿔 끼운 데이터 생성 차단, 다른 사용자의 이미지 저장 경로에 올리기·읽기 차단, 로그인하지 않은 사용자의 읽기 차단.
- **남은 것**: "첨부 동작"은 업로드 화면이 있어야 사람이 직접 확인할 수 있어서 D3에서 편집 화면에 이미지 첨부를 붙일 때 확인한다. 업로드 요청 제한과 중복 업로드 방지는 D3·D6에서 만든다.
## 2026-10-08 — D3 첫 단계: 폴더·프로젝트 저장, 자동 저장, 충돌 안내

- **정한 것**:
  - API(spec 11장): `GET/POST /api/folders`, `PATCH/DELETE /api/folders/:id`, `GET/POST /api/projects`, `GET/PATCH /api/projects/:id`, `POST /api/projects/:id/move`. 모두 로그인한 사용자의 세션으로 동작해서 RLS가 적용되고, 요청 본문은 서버에서 Zod로 검사한다. 남의 데이터와 없는 데이터는 같은 404로 답한다.
  - 폴더 삭제(spec F02): 프로젝트가 들어 있으면 409를 돌려주고, `?moveToUnsorted=true`일 때만 프로젝트를 미분류로 옮긴 뒤 폴더를 삭제 처리(휴지통)한다. 프로젝트는 폴더와 함께 지워지지 않는다.
  - 저장(spec 10.3): `PATCH /api/projects/:id`는 `expected_revision`이 현재 revision과 같을 때만 갱신하고, 다르면 409와 서버의 최신 revision을 돌려준다. revision은 DB 트리거가 올린다.
  - 자동 저장은 화면과 분리한 `Autosaver`(`src/lib/autosave.ts`)로 만들었다. 마지막 입력 1초 뒤에 저장하고, 요청은 한 번에 하나만 보내며, 저장 중에 새로 입력하면 끝난 뒤 이어서 저장한다. 상태는 대기 중(dirty)·저장 중·저장됨·저장 실패·충돌이고, 응답이 현재 입력과 같을 때만 "저장됨"으로 표시한다. 단계를 옮기거나 입력 칸을 벗어나면 기다리지 않고 저장하고, 저장하지 못한 내용이 있으면 탭을 닫을 때 브라우저 경고를 띄운다.
  - 실패하면 입력은 화면에 그대로 두고 "다시 시도"를 보여 준다. 충돌이면 저장을 멈추고(자동 덮어쓰기 없음) 닫을 수 없는 안내 창에서 "최신 버전 열기"(저장된 내용으로 다시 불러옴) 또는 "내 입력 복사"를 고르게 한다.
  - 화면: 로그인하면 사이드바와 보관함에 샘플 대신 실제 폴더·프로젝트가 보이고, 새 폴더·새 프로젝트(제목·폴더·기간·유형)·폴더 이름 변경·삭제·프로젝트 폴더 이동 창이 열린다. 데이터가 없으면 빈 보관함 안내가 보인다. 로그인 전에는 지금처럼 샘플과 로그인 안내가 보인다. 편집 화면에서는 제목을 직접 고칠 수 있다(비우면 이전 제목 유지).
- **이유**: spec 6장 F02·F03·F07, 10.3, 11장 및 20장 지침(한 프로젝트의 생성→입력→저장→재열기 흐름을 먼저 완성)을 따랐다. 저장 순서가 꼬이면 입력이 사라지므로 로직을 화면에서 분리해 단위 테스트로 검증했다.
- **다른 선택지**: 서버 컴포넌트에서 직접 DB를 읽기(로그인 전 샘플과 로그인 후 실제 데이터를 한 화면에서 구분하기 어려움), 입력마다 즉시 저장(요청이 폭주하고 순서가 꼬임), 충돌 시 자동 병합·덮어쓰기(spec이 금지).
- **확인한 것**: `Autosaver` 단위 테스트 9개(디바운스, 저장 중 입력, 중복 요청 금지, 실패·재시도, 충돌 정지 등)와 전체 테스트 32개가 통과한다. 로그인 없이 7개 API가 모두 401을 돌려준다. 브라우저에서 가짜 로그인 상태와 가짜 서버 응답을 주입해 화면을 점검했다: 폴더·프로젝트 만들기(입력 오류 안내 포함), 자동 저장(디바운스로 요청 1건, revision 증가, 단계 이동 시 즉시 저장), 오프라인 실패와 재시도, 충돌 안내와 최신 버전 열기, 폴더 이름 변경·삭제(미분류로 이동), 프로젝트 이동. 점검 중 발견한 문제(입력 직후에도 "저장됨"으로 표시)는 '저장 대기 중' 상태를 추가해 고쳤다.
- **아직 확인하지 못한 것**: 실제 Supabase에 대한 저장은 실제 Google 로그인으로만 확인할 수 있어 사용자가 직접 확인해야 한다. 휴지통(프로젝트 삭제·복원·영구 삭제)과 이미지 첨부는 다음 단계에서 만든다.
## 2026-10-08 — 비로그인도 로그인한 사람과 같은 화면(샘플 없음), 저장만 안 됨

- **정한 것**:
  - 로그인하지 않은 사용자도 샘플 화면이 아니라 로그인한 사용자와 같은 보관함·편집 화면을 쓴다. 빈 보관함에서 시작해서 폴더와 프로젝트를 직접 만들고, 이름을 바꾸고, 폴더를 옮기고, 질문에 답하고, 미리보기를 볼 수 있다. 이전에 만든 샘플 데이터(`src/lib/sample`)와 샘플 빈 화면(`/workspace/empty`)은 지웠다.
  - 비로그인 상태의 내용은 브라우저 메모리에만 둔다(`WorkspaceDataProvider`의 `local` 모드). 새로고침하거나 창을 닫거나 로그인하면 사라진다. 로그인한 사용자(`real` 모드)와 같은 대화 상자·목록·편집기를 쓰고, 편집기만 "서버에 자동 저장" 대신 "메모리에 반영"으로 동작한다.
  - 저장되지 않는다는 점을 숨기지 않는다. 보관함 위쪽 안내, 사이드바 아래 문구, 편집 화면의 "저장되지 않음 · 로그인하면 저장돼요", 내용이 있는 채로 창을 닫을 때의 브라우저 경고, 새로고침 뒤 프로젝트 주소를 열었을 때의 안내 화면이 그렇다. "저장" 버튼을 누르면 로그인 안내 창이 뜬다. 로그인하러 가는 이동에는 창 닫기 경고를 띄우지 않는다.
  - 이미지 첨부는 저장소가 필요하므로 로그인한 뒤에만 쓴다.
  - spec.md를 v0.5로 올렸다(F15 "로그인 없이 써 보기"로 바꾸고 8.1 설명 수정).
- **이유**: 사용자가 비로그인 사용자에게 샘플이 아니라 로그인한 사람과 같은 화면을 보여 주고, 직접 써 볼 수 있되 저장만 안 된다고 알리기를 원했다. 서비스를 직접 체험해 본 뒤 저장하고 싶을 때 로그인하게 하려는 목적이다.
- **다른 선택지**: 샘플 데이터를 보여 주는 둘러보기(이전 방식), 체험 내용을 브라우저에 보관했다가 로그인 후 서버로 옮겨 주기(sessionStorage 사용. 로그인하면 사라지는 문제는 줄지만 공용 컴퓨터에 내용이 남을 수 있어 이번에는 하지 않음).
- **알아둘 점**: 체험 중에 만든 내용은 로그인하면 사라진다. 사용자가 이를 불편해하면 "로그인 직전에 지금 내용을 임시로 옮겨 두었다가 로그인 후 자동으로 저장" 기능을 추가할 수 있다(별도 결정 필요).
## 2026-10-08 — D3 둘째 단계: 휴지통(삭제·복원·영구 삭제)과 30일 자동 정리

- **정한 것**:
  - 삭제(spec F13): 프로젝트와 폴더는 바로 지우지 않고 삭제 표시(`deleted_at`)만 한다. `DELETE /api/projects/:id`로 프로젝트를 휴지통에 보낸다. 폴더 삭제는 앞 단계의 방식(안의 프로젝트는 미분류로 옮기고 폴더를 휴지통에 보냄) 그대로다.
  - 휴지통 API: `GET /api/trash`(30일 안에 삭제한 프로젝트·폴더와 프로젝트의 원래 폴더), `POST /api/trash/:type/:id/restore`, `DELETE /api/trash/:type/:id/purge`. 영구 삭제는 휴지통에 있는 항목만 지울 수 있고, 사용 중인 항목은 이 경로로 지울 수 없다.
  - 복원: 프로젝트의 원래 폴더가 없어졌거나 삭제 상태이면 미분류로 복원하고 "원래 폴더가 없어서 미분류에 있어요"라고 알린다. 폴더를 복원해도 그 폴더에서 나온 프로젝트들이 자동으로 돌아오지는 않는다(spec이 정하지 않아 가장 단순한 규칙으로 했다).
  - 영구 삭제는 되돌릴 수 없어서 확인 창에서 한 번 더 묻는다.
  - 화면: 사이드바의 "휴지통 · 30일 보관" 링크와 `/workspace/trash`(종류별 탭 전체·프로젝트·폴더, 원래 위치, 삭제일, 남은 날수, 3일 이하이면 빨간색). 보관함의 프로젝트 행에 "삭제" 버튼을 넣었다. 비로그인 체험 중에도 같은 화면과 동작이며 이 휴지통도 저장되지 않는다.
  - 30일 자동 정리: spec 10.2는 "서버에서 하루 1회"라고만 정했고, Vercel Cron 대신 Supabase 안의 pg_cron으로 하기로 했다(`supabase/migrations/20261008010000_trash_purge_job.sql`). 매일 한국 시간 03:00에 삭제한 지 30일이 지난 프로젝트·폴더 행을 지운다.
- **이유**: Vercel Cron으로 하면 사용자 없이 데이터를 지우는 요청에 관리자 키(secret key)가 필요하다. pg_cron은 데이터베이스 안에서 돌아서 관리자 키를 서버 코드에 두지 않아도 되고(spec 12.2 방침), 설정이 한 번의 SQL 실행으로 끝난다.
- **다른 선택지**: Vercel Cron + 관리자 키(키 관리 부담과 노출 위험), 자동 정리 없이 사용자가 직접 비우기(spec 위반), 휴지통 비우기 버튼(spec에 없어 이번에는 제외).
- **알아둘 점**:
  - pg_cron은 데이터베이스의 행만 지운다. 프로젝트에 붙은 이미지 파일(스토리지)은 이미지 첨부를 만들 때 서버 작업으로 따로 정리한다(지금은 첨부 기능이 없어 남는 파일이 없다).
  - 자동 정리 SQL은 사용자가 Supabase에서 한 번 실행해야 효력이 있다.
  - 확인한 것: 날짜 계산 단위 테스트 4개와 전체 테스트 36개가 통과한다. 비로그인 체험에서 삭제→휴지통→복원→폴더 삭제 뒤 복원(미분류)→영구 삭제(취소 시 유지, 확인 시 삭제)를 브라우저로 확인했다. 로그인한 상태는 가짜 서버로 삭제·목록·복원·미분류 복원·영구 삭제가 올바른 주소로 요청되고 화면이 갱신되는 것을 확인했다. 점검 중 발견한 문제(휴지통 불러오기 실패 시 다시 시도 버튼이 없음)는 버튼을 추가해 고쳤다. 실제 Supabase에서의 동작은 사용자가 직접 확인해야 한다.

## 2026-10-08 — D6-1: 요청 제한과 업로드 중복 방지

- **정한 것**:
  - **요청 제한(spec 14장)**: 업로드 계정당 분당 10회, 일반 쓰기(POST/PATCH/DELETE) 분당 120회. DB 함수 `take_rate_limit`이 계정·종류별로 1분 칸에 횟수를 센다(`rate_limit_hit`, 사용자는 표를 직접 읽거나 쓸 수 없고 함수만 부른다). 넘으면 429와 "N초 뒤에 다시 시도" 문구, `Retry-After` 머리글을 준다. 읽기(GET)는 세지 않는다. 한도 함수 자체가 실패하면 저장을 막지 않고 서버 기록만 남긴다(제한 장치 때문에 데이터를 잃지 않도록).
  - **업로드 중복 방지(spec 11장 operation ID)**: 브라우저가 업로드마다 작업 번호를 만들어 보내고, 서버가 `client_operation`에 먼저 등록한다. 같은 번호가 다시 오면 새로 만들지 않고 처음 결과를 돌려준다(처리 중이면 409). 실패하면 번호를 풀어 다시 시도할 수 있게 한다. 브라우저는 네트워크가 끊기면 같은 번호로 한 번 더 보낸다.
  - 파일: `supabase/migrations/20261008030000_rate_limit_and_dedupe.sql`, `supabase/tests/rate-limit.sql`, `src/lib/api/rate-limit.ts`, `getAuthed(request, bucket?)`.
- **이유**: spec 14장 요청 제한, 11장 중복 생성 방지.
- **다른 선택지**: Vercel/Upstash 같은 외부 제한 서비스(키·비용 추가), 메모리 카운터(서버리스라 인스턴스마다 달라 동작하지 않음).
- **알아둘 점**: 이 SQL을 실행하기 전에는 요청 제한이 꺼진 채로 동작하고(막지 않음), 이미지 업로드는 작업 번호 등록에 실패해 409로 거절된다. 실행 후 `supabase/tests/rate-limit.sql`로 검사한다.

## 2026-10-08 — 프로젝트 작성 화면 개선 (문구·작성 위치 강조·저장 안내·단계 상태·미리보기 접기)

- **정한 것** (사용자 요청 순서대로):
  1. **문구**: 상단 "1/10 단계 · 프로젝트 개요", 보조 문구 "모든 질문에 답하지 않아도 괜찮아요. 필요한 내용부터 작성해 보세요."(헤더 아래 작은 글씨). 프로젝트 개요의 질문 3개 목록은 입력 칸과 겹쳐서 빼고 "이 프로젝트가 무엇인지, 왜 시작했는지부터 정리해 보세요."로 대체(`StepDefinition.intro`, 개요 단계만). "회색 글씨는 작성 예시예요. 필요한 항목부터 자유롭게 작성해 보세요." 입력 칸 문구: "프로젝트 한 줄 소개", "어떤 프로젝트를 진행했나요?", "이 프로젝트를 시작한 이유는 무엇인가요?"(데이터 필드 이름·저장 구조는 그대로). 미리보기: "포트폴리오 미리보기 · 프로젝트 소개"(분석·실행·결과), 배지 "작성 위치", 빈 구역 "작성한 내용이 여기에 표시돼요.", 아래 안내 "작성한 내용이 포트폴리오에 어떻게 배치될지 미리 확인할 수 있어요." 실제 입력 내용이 있으면 그대로 보인다.
  2. **작성 위치 강조**: 입력 항목에 포커스가 가면 그 항목이 들어갈 구역 하나만 파란 테두리·"작성 위치" 배지로 강조한다(전에는 섹션의 여러 구역이 함께 강조됨). 항목→구역 연결은 템플릿(`FIELD_ZONE`, `zoneOfField`, `pageOfZone`)에 있고, 한 섹션이 여러 구역에 걸치는 경우(개요: 프로젝트 정보/개요·선정 이유, 해결안: Solution/대안과 선택 이유, 진행 상태→프로젝트 정보)만 항목별로 지정한다. 구역이 다른 페이지에 있으면 미리보기 페이지도 따라 바뀐다. 기존 페이지 이동 버튼은 그대로.
  3. **저장 안내**: 비회원은 "체험 중 · 저장되지 않아요" + 파란 "로그인하고 저장" 버튼(누르면 기존처럼 로그인 안내 창), 로그인 사용자는 "자동 저장됨/저장 중…/저장 실패…"로 구분한다. 저장 로직·인증은 변경하지 않았다(로그인 사용자의 저장은 이미 자동 저장으로 동작). 헤더는 "제목 + 저장 묶음(상태·버튼·기록 상태)"과 "현재 단계 + 단계 선택 묶음", 보조 안내, 진행률 막대 순서로 정리했다.
  4. **단계별 상태**: 단계 선택 목록과 현재 단계 옆에 "작성 전 / 작성 중 / 작성 완료"를 표시한다(`src/lib/step-status.ts`). 작성 전=그 단계 입력이 모두 비어 있음, 작성 완료=단계의 주요 항목이 모두 채워짐, 나머지=작성 중. 주요 항목: 개요(한 줄 소개·프로젝트 설명·시작 이유), 역할(맡은 범위·수행 항목 1개 이상), 문제(현상·중요성), 근거(설명 1개 이상), 인사이트(패턴·해석), 가설(이유·예상 행동), 해결안(개선 내용·선택 이유), 지표·결과(지표 이름·결과 상태·결과 요약), 실행(진행 순서·협업 방법), 회고(배운 점·다음 단계). 품질 점수가 아니며 단계 이동은 막지 않는다.
  5. **미리보기 접기**: 넓은 화면(1,280px 이상)에서 "미리보기 접기"로 입력 영역을 넓히고(최대 896px 한 열) "미리보기 펼치기"로 되돌린다. 입력 내용과 현재 단계는 그대로이고 화면에서만 숨긴다. 좁은 화면은 이미 "작성/미리보기" 탭이라 접기 버튼을 두지 않는다. 새로고침하면 펼친 상태로 돌아간다.
  6. **작성 예시(회색 글씨)**: 모든 글 입력 칸에 한두 문장짜리 구체적인 예시를 달았고(같은 예시 프로젝트 "신규 사용자 온보딩 개선" 기준), 저장되지 않는다(입력 칸의 placeholder). 요청에 적힌 두 예시 문장은 그대로 썼다. 질문 문구가 바뀐 개요 단계는 랜딩의 10단계 소개 카드에도 같은 문구가 보인다.
- **확인한 것**: 단위 테스트 102개 통과(단계 상태 규칙, 모든 입력 항목이 실제 구역·페이지에 연결되는지 등 새 테스트 포함), 린트·빌드 통과. 체험 모드 브라우저에서 헤더 문구, 포커스에 따른 한 구역 강조(개요: 시작 월→프로젝트 정보, 설명→개요·선정 이유), 단계 상태가 작성 전→작성 중→작성 완료로 바뀜, 미리보기 접기·펼치기 후 입력값·단계 유지, 360px에서 가로 넘침·작은 터치 요소 없음을 확인했다. 로그인 상태의 저장 표시와 PDF 출력은 코드를 바꾸지 않았고 직접 확인하지 않았다.

## 2026-10-09 — PDF 프로젝트 소개 페이지를 새 디자인으로 (실제로 만들기)

- **정한 것**(사용자: 참고 이미지처럼 실제로 만들고 싶다, 1~3번만): 포트폴리오 PDF의 **프로젝트 소개 첫 장**을 새 디자인으로 바꿨다. 위쪽 영역(`hero`): "프로젝트 소개" 알약, 큰 제목(프로젝트 이름), 파란 둘째 줄(성과 **목표**), 오른쪽 대표 이미지, 정보 카드 3개(프로젝트 기간·주요 역할·프로젝트 유형(+팀 규모)), 파란 "한 줄 소개" 상자. 그 아래 남은 자리에 개요·선정 이유·역할 설명이 두 단으로 흐른다. 글자와 구조는 실제 PDF 렌더러(`PageFrame`)에서 그린다.
  1. **범위**: 소개 페이지만 먼저. 표지·분석·실행·결과 페이지는 아직 예전 모양(같은 스타일로 맞추는 것은 이 페이지를 확인한 뒤에 정한다). 4번(왼쪽 목차·1/9 넘김)은 하지 않는다(사용자 결정).
  2. **파란 둘째 줄 = 성공 지표의 "기준 → 목표"**: 지표 이름과 목표값이 있는 지표 중 "성공 지표"를 먼저 골라 "첫 설정 완료율 · 기준 42% → 목표 55%"로 쓴다(확인한 실제 값이 있을 때만 "· 실제 …"를 덧붙인다). 결과처럼 쓰지 않는다(spec 9.2). 지표가 없으면 이 줄은 없다. 사용자가 실행 페이지에서 "목표·검증 지표"를 숨겼거나 실행 페이지를 뺐다면 소개에도 올리지 않는다(숨긴 내용을 다른 곳에서 보이게 하지 않는다).
  3. **오른쪽 그림 자리 = 대표 이미지**: 출력에 포함하기로 한 대표 이미지가 있으면 오른쪽에 크게(최대 300×190), 없으면 비워서 글이 넓게 나온다. 지어낸 일러스트는 쓰지 않는다.
- **같은 말을 두 번 쓰지 않는다**: 위쪽에 나온 제목·정보·한 줄 소개·대표 이미지·역할 이름은 본문에서 뺀다. 개요 설명·선정 이유·역할 설명은 본문에 남는다. 개요·역할 섹션을 모두 숨기면 위쪽 영역 없이 예전 모양이다(그 경우 보일 내용이 없으면 페이지도 없다).
- **페이지 나누기**: 위쪽 영역이 첫 장의 자리를 차지하므로 첫 장은 들어갈 자리가 적다(`paginate`에 첫 장용 `fitsFirst` 추가). 위쪽 영역 때문에 본문 첫 묶음이 첫 장에 못 들어가도 다음 장에 들어가면 "넘침"으로 표시하지 않고 이어짐 장으로 보낸다. 위쪽 영역은 첫 장에만 붙는다. 대표 이미지도 불러오기 실패를 점검한다.
- **랜딩**: 첫 화면의 포트폴리오 한 장을 이 실제 디자인으로 교체했다(이제 "이렇게 만들어져요"가 사실이다). 성과는 "기준 42% → 목표 55%"로만 쓴다.
- **확인한 것**: 타입·린트·빌드 통과, 테스트 119개 통과(소개 위쪽 영역 11개·나누기 6개 등 새 테스트 17개 포함). 체험 모드에서 프로젝트를 쓰고 포트폴리오에 담아 미리보기까지 가서 새 소개 페이지(제목·파란 목표 줄·카드 3개·한 줄 소개·개요·역할)가 한 장에 맞게 나오고 실행 페이지가 이어지는 것을 화면으로 확인했다. 대표 이미지(로그인 필요)는 실제 업로드로는 확인하지 못했고 테스트로 확인했다.

## 2026-10-13 — AI로 초안 채우기: 사용자가 자기 AI에 붙여 넣는 방식으로 변경 (spec F16, 서버 방식 폐기)

- **걷어낸 것**: `POST /api/ai/pdf-draft`, `@anthropic-ai/sdk` 의존성, AI 요청 제한 SQL(`20261013010000_rate_limit_ai.sql`), `ANTHROPIC_API_KEY`·`ANTHROPIC_MODEL` 환경변수. 커밋하기 전이라 저장소 기록에는 남지 않았다. 나중에 서버 방식이 필요해지면 다시 만든다(그때는 키·비용·하루 총량 제한부터 정한다).
- **이유**: 서버 방식은 호출마다 키 주인(사용자)에게 요금이 청구되고, 방문자가 쓰면 총액에 상한이 없다. 복사·붙여넣기 방식은 요금이 없고, 서버가 문서를 받지 않아 개인정보 설명도 단순하다(문서는 사용자가 직접 고른 AI에만 올라간다). 오늘 제출 일정에도 안전하다.
- **유지한 것**: 지침의 규칙(문서에 없는 내용·숫자·성과·기여율·링크·실제 값 만들지 않기, 계획 문서의 결과를 달성으로 쓰지 않기, 문서 속 지시문 따르지 않기, 개인정보 옮기지 않기)과 병합 규칙(이미 쓴 칸 불변, 목록은 비어 있을 때만, 글자 수·기간·선택값 검증).
- **단점**: 복사·붙여넣기가 두 번 필요해 "자동"은 아니다. AI가 JSON 형식을 틀리면 오류 안내 후 다시 시켜야 한다(조금 틀린 형식·빠진 키·잘못된 선택값은 읽을 수 있는 만큼 읽고 모르는 값은 비운다). 결과의 품질은 사용자가 쓰는 AI에 달려 있다.
- **spec 변경**: v0.7. F16을 "AI로 초안 채우기"로 바꾸고, 4장·12장·13장의 서버 방식 문구(Anthropic API, 요청 제한)는 되돌렸다. `/privacy`에는 "이 서비스는 문서를 받지 않는다, 사용자가 고른 AI에서의 보관은 그 회사 정책을 따른다"를 적었다.
- **확인한 것**: 린트·타입·테스트 통과(병합 7개 + 지침·붙여넣기 읽기 9개). 브라우저(로그인 없이)에서 카드·안내 창, 지침 3,011자와 JSON 견본, 복사 권한이 없을 때의 직접 선택 안내, JSON이 아닌 글의 오류 문구, 코드블록과 설명이 붙은 정상 결과 붙여넣기(빈 칸 12곳 채움, 직접 쓴 한 줄 소개는 그대로)를 확인했다. **실제 AI(ChatGPT·Claude)에 지침을 붙여 넣어 나온 결과로는 시험하지 못했다**(사용자 시험 필요).

## 2026-10-13 — AI로 초안 만들기 문구(UX Writing) 개선
- **정한 것**: 사용자가 정한 문구로 카드·안내 창·결과·오류 안내를 바꿨다(자세한 문구는 `docs/design.md`). 기능 로직, 데이터 처리, JSON 읽기, 레이아웃은 그대로다.
- **로직에 닿은 부분은 이것뿐이다**: 채울 항목이 0개일 때 "AI 결과에 가져올 내용이 없었음"과 "채울 빈 항목이 없었음"을 구분해 문구만 다르게 보여 준다(같은 병합 함수로 빈 답변에 합쳐 보는 계산만 더했고 사용자 데이터는 바꾸지 않는다). 개수는 실제로 채운 항목 수다.
- **참고**: 카드 설명의 "핵심 내용을 추출해"는 서비스가 문서를 직접 읽는 것처럼 읽힐 수 있다. 안내 창이 "AI에 기획서와 지침 보내기" 흐름을 분명히 보여 주므로 그대로 두었다. 오해가 보이면 "AI로 추출한 결과를 붙여넣어" 같은 표현으로 바꿀 수 있다.
- **확인한 것**: 브라우저에서 모든 문구, 3가지 오류 안내, 성공("13개 항목에 초안을 채웠어요")과 같은 결과를 다시 넣었을 때("채울 수 있는 빈 항목이 없어요"), 내용 없는 결과("가져올 내용을 찾지 못했어요")를 확인했다. 린트·타입·테스트 통과.

## 2026-10-13 — 다음 단계로 가는 작은 아이콘, AI 카드 줄바꿈 정리
- **정한 것**: 이전·다음 단계 버튼이 입력 칸 맨 아래에만 있어 잘 안 보인다는 의견에 따라, 단계 제목 오른쪽에 작은 `←`·`→` 아이콘(`aria-label` "이전 단계로"·"다음 단계로", 각 터치 영역 44px)을 더했다(처음에는 `→`만 두었다가 사용자 요청으로 `←`도 추가했고, 1단계에서 `←`가 안 보여 없는 것처럼 느껴진다는 의견에 따라 양쪽을 항상 보이게 하고 끝 단계에서만 흐리게 비활성 처리했다). 처음에는 오른쪽 진행 카드에 이전·다음 버튼을 넣었지만 사용자가 빼 달라고 해서 되돌렸다. 아래쪽 버튼은 그대로다. AI 초안 카드 설명이 "…보세/요."처럼 끊기던 것은 단어 단위 줄바꿈으로 고쳤다.
- **다른 선택지**: 진행 카드에 이전·다음 버튼(사용자가 원하지 않아 제외), 아래쪽 버튼 없애기(긴 입력을 마친 뒤 바로 다음으로 가기 불편).
- **확인한 것**: 1600px에서 아이콘이 제목과 같은 줄 오른쪽에 있고(44×44), 누르면 1→2단계로 바뀐다. 진행 카드에는 이전·다음 버튼이 없고 단계 선택칸은 그대로다. 마지막 단계(10/10)에서는 아이콘이 없고 아래쪽 "포트폴리오 만들기" 링크가 있다. 1280px(사이드바 열림)에서 카드 설명이 단어째로 나뉜다. 린트·타입 통과.

## 2026-10-13 — AI 초안 지침: 핵심만 간결하게 쓰도록 변경
- **정한 것**: AI가 칸마다 너무 길게 채운다는 의견에 따라 `지침 복사하기`로 복사되는 지침의 분량 규칙을 바꿨다(`src/lib/ai/draft-schema.ts`의 규칙 5). 한 칸은 짧은 문장 1~3개(150자 안팎), 한 줄 소개 60자·제목류 30자 이내, 목록(기여·근거·지표)은 핵심 3~5개를 한 줄씩, 상한(2,000자)은 채우라는 뜻이 아님, 분량 예시 한 줄(내용에는 쓰지 말라고 명시). 견본 안내의 목록 개수도 "최대 10개·6개"에서 "핵심 3~5개"로 바꿨다.
- **이유**: 이전 지침은 칸당 2,000자 이하라고만 적어서, AI가 문서 문장을 길게 옮기고 상한 가까이 채웠다. 상한을 숫자로 알려 주면 그만큼 쓰라는 신호로 읽히기 쉽다.
- **바꾸지 않은 것**: 앱의 글자 수 상한(칸당 2,000자 등)과 붙여넣은 결과를 자르는 규칙. 긴 결과를 앱이 중간에서 잘라 문장이 끊기는 것보다, 지침으로 처음부터 짧게 받는 쪽을 택했다.
- **알아둘 점**: 이미 복사해 둔 예전 지침은 그대로라서 `AI로 초안 만들기`를 다시 열어 새 지침을 복사해야 한다. AI마다 지키는 정도가 다르므로 그래도 길면 AI에게 "더 짧게, 핵심만 다시 써 줘"라고 요청하면 된다. 실제 AI 결과의 분량은 아직 시험하지 못했다.
- **확인한 것**: 지침 테스트(핵심만·150자 안팎·60자 이내·3~5개·채우라는 뜻이 아님, 최대 개수 문구 없음) 포함 테스트 통과, 타입·린트 통과.
